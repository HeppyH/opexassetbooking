# Phase 14.1 – Tenant Validation for AddInId Implementation

**Repository:** `C:\04. Project 2026\Geotab\Book Vehicle\opex-vehicle-booking-clone`
**Target Tenant:** `opex_trial` (test database only)
**Status:** BLOCKED — Administrator access to `opex_trial` not available in this environment

## 1. Purpose

Validate the AddInId implementation in the live `opex_trial` MyGeotab tenant. This procedure performs a **read-only Get first**, then a **controlled test Add** only after administrator approval. No existing records are deleted, overwritten, or migrated.

## 3. Validation Procedure

### Phase A: Read-Only Verification (Safe, No Data Modification)

**Step A1: Confirm Add-In Registration**
1. Log in to MyGeotab `opex_trial` as administrator
2. Navigate to System Settings → Add-Ins
3. Confirm "OPEX Asset Booking" Custom-page Add-In is registered
4. Record the AddInId shown in the Add-In details

**Step A2: Configure Application AddInId**
1. Open the OPEX Vehicle Booking Add-In from MyGeotab menu
2. Enter the recorded AddInId in the AddInId field
3. Click Save
4. Verify the app shows ADDIN_DATA mode (not DEMO)

**Step A3: Read-Only Get Test**
1. Open the browser Developer Console (F12)
2. Run a read-only AddInData Get:
   ```javascript
   // Example: query AddInData records scoped to the AddInId
   geotab.api.call("Get", {
     typeName: "AddInData",
     search: { addInId: "<YOUR_ADDIN_ID>" },
     resultsLimit: 10
   }, (result) => {
     console.log("AddInData Get result:", result);
   }, (error) => {
     console.error("AddInData Get error:", error);
   });
   ```
3. Verify the call succeeds (no `GEOTAB_API_ERROR`, no `ADDIN_ID_NOT_CONFIGURED`)
4. Verify the response contains records scoped to your AddInId (or empty array if none exist)
5. **Do not write, modify, or delete any records**

### Phase B: Controlled Test Add (Administrator Approval Required)

**STOP:** Only proceed after explicit administrator approval. This creates one test record in AddInData.

**Step B1: Create Test Record**
1. In the application, create a test booking with clearly identifiable data (e.g., purpose: "TEST_ADDIN_VALIDATION")
2. Verify the booking appears in the bookings list
3. Verify the booking status is `PENDING_APPROVAL`

**Step B2: Verify Record Persistence**
1. Refresh the page
2. Verify the test booking still appears (persisted in AddInData)
3. Verify the AddInData record is scoped to the correct AddInId

**Step B3: Clean Up Test Record**
1. Delete the test booking through the application UI
2. Verify it no longer appears in the list

## 4. Success Criteria

| Criterion | Pass/Fail | Notes |
|-----------|-----------|-------|
| AddInId is NOT `opex_trial` | | Must be the value generated by MyGeotab registration |
| Custom-page Add-In loads in MyGeotab iframe | | No `API not available` error |
| AddInData Get succeeds with correct addInId | | Returns records or empty array, no error |
| AddInData Add succeeds | | Creates record scoped to correct addInId |
| Service Add-In polls AddInData | | `serviceAddin.js` loaded at configured `serviceSrc` URL |
| Native notification delivery | | `service.notifications.show()` delivers toast (if available in tenant) |
| Both Add-Ins use same AddInId | | Custom-page and Service Add-In configured identically |

## 5. Failure Modes

| Symptom | Likely Cause | Resolution |
|---------|-------------|------------|
| `ADDIN_ID_NOT_CONFIGURED` | addInId is null/empty | Enter valid AddInId in app UI |
| `GEOTAB_API_ERROR` | API not injected | Add-In not loaded inside MyGeotab context |
| Records not found | Wrong addInId | Verify AddInId matches registration |
| Service Add-In not polling | `serviceAddin.js` not deployed | Deploy bundle to `serviceSrc` URL |
| `service.notifications.show()` undefined | SDK version | Verify MyGeotab SDK supports Notifications service |

## 6. What Is NOT Validated Here

- MyGeotab Device/User/Trip/LogRecord API access (requires separate identity configuration)
- PostgreSQL/Neon integration (not used — AddInData is the only persistent storage)
- Cloudflare Workers API (future backend, not part of this phase)
- Cross-context `localStorage` sharing between Custom-page and Service Add-In (requires live tenant test)

## 7. Rollback

No rollback needed. This procedure:
- Does not delete existing AddInData records
- Does not overwrite records under any AddInId
- Does not migrate records between namespaces
- Creates and deletes only one controlled test record (with approval)

## 8. Handoff

Provide the administrator with:
1. The AddInId generated during registration
2. Confirmation that `DEFAULT_ADDIN_ID` in code matches (or differs from) the generated value
3. The `serviceAddin.js` deployment URL
4. The test results from Phase A and Phase B
